# balance-game

"평생 민초만 먹기 vs 평생 파인애플 피자만 먹기"

둘 중 하나를 골라 투표하고, 다른 사람들의 선택을 확인하는 밸런스 게임 사이트입니다.
Django 강의에서 배운 내용을 바탕으로 처음부터 직접 설계하고 배포합니다.
화면은 Next.js로 만들고, Django는 REST API 서버로 사용합니다.

## 프로젝트 목표
- 강의를 따라 치지 않고 모델 설계부터 직접 해보기
- `ForeignKey`, 로그인, 권한, 테스트처럼 강의 노트에 없던 내용 익히기
- Django REST Framework로 API를 설계하고 Next.js와 연결하기
- 처음부터 PostgreSQL로 개발하기
- 실제로 배포해서 친구들이 링크로 쓰게 만들기

## 만드는 기능

### 핵심 기능
- 회원가입, 로그인, 로그아웃
- 두 선택지가 있는 질문 등록
- 질문 목록과 상세 화면
- 1인 1표 투표
- 투표 후 선택지별 득표율 확인

### 추가 기능
- 내가 만든 질문 수정·삭제
- 댓글
- 인기순·최신순 정렬
- 랜덤으로 다음 질문 보기
- "내 선택은 소수파 12%" 같은 결과 문구

### 지금은 만들지 않는 것
- 소셜 로그인
- JWT 인증
- 실시간 결과 갱신
- 이미지 업로드

## 구조

```text
balance-game/
├── backend/   # Django, Django REST Framework
├── frontend/  # Next.js
├── guide/     # 챕터별 가이드북
└── notes/     # 막혔던 내용 정리
```

```text
브라우저 → Next.js → /api/* 요청을 rewrites로 전달 → Django → PostgreSQL
```

- **인증:** JWT 대신 Django 세션을 사용한다. 브라우저는 Next.js 주소로만 요청하므로 같은 출처로 동작하고, CORS 설정이 필요 없다.
- **데이터 조회:** 로그인 상태나 투표 여부에 따라 달라지는 화면은 클라이언트 컴포넌트에서 조회한다. 공유 미리보기처럼 사용자 정보가 필요 없는 데이터만 서버에서 조회한다.
- **Django Template:** 서비스 화면에는 사용하지 않는다. Django Admin은 그대로 사용한다.

### 01. 회원가입과 로그인
**목표:** Django 세션 인증으로 회원가입부터 로그아웃까지 Next.js 화면에서 동작하게 한다.

- [ ] 회원가입, 로그인, 로그아웃 API
- [ ] 현재 사용자를 확인하는 `GET /api/auth/me`
- [ ] CSRF 쿠키를 발급하는 `GET /api/auth/csrf`
- [ ] 쓰기 요청에 `X-CSRFToken` 헤더 포함
- [ ] 로그인·회원가입 API에 `csrf_protect` 적용
- [ ] 회원가입, 로그인 화면
- [ ] 상단 메뉴에 로그인 상태 표시
- [ ] `IsAuthenticated` 사용해 보기
- [ ] 미인증 응답을 받으면 로그인 화면으로 이동
- [ ] `APIClient`로 인증 흐름 테스트 작성

**완료 기준**
- 비로그인 사용자가 보호된 페이지에 들어가면 로그인 화면으로 이동한다.
- 비로그인 상태로 보호된 API를 직접 호출하면 거부된다.
- 잘못된 비밀번호로는 로그인되지 않는다.
- 새로고침해도 로그인 상태가 유지된다.

> DRF는 비로그인 요청의 CSRF를 검사하지 않으므로 로그인·회원가입 API에는 `csrf_protect`를 직접 적용한다. 세션 인증의 미인증 응답은 401이 아니라 403으로 올 수 있고, 로그인 후에는 CSRF 토큰이 바뀌므로 요청마다 쿠키에서 읽어 보낸다.

### 02. 질문 등록과 조회
**목표:** `Question` 모델을 직접 설계하고, 작성자와 `ForeignKey`로 연결한다.

- [ ] `Question` 모델 설계 후 리뷰받기
- [ ] Django Admin 등록
- [ ] Serializer로 입력 검증
- [ ] 질문 목록, 상세, 등록 API
- [ ] 등록할 때 작성자를 서버에서 자동 저장
- [ ] 질문 목록, 상세, 등록 화면
- [ ] 입력 검증과 API 테스트 작성

**완료 기준**
- 로그인한 사용자만 질문을 등록할 수 있다.
- 요청에 다른 작성자를 넣어도 로그인한 사용자로 저장된다.
- 두 선택지가 같은 내용이면 등록되지 않는다.
- 없는 질문을 조회하면 API는 404를 응답하고, 화면에는 404 페이지가 나온다.

### 03. 투표와 결과
**목표:** 1인 1표를 애플리케이션과 DB 양쪽에서 보장하고, 결과를 집계한다.

- [ ] `Vote` 모델 설계 후 리뷰받기
- [ ] `UniqueConstraint`로 중복 투표 방지
- [ ] 투표 API는 POST 요청만 받기
- [ ] 동시 요청으로 생기는 `IntegrityError` 처리
- [ ] `annotate`, `Count`로 득표수 집계
- [ ] 투표한 사람의 API 응답에만 득표수와 득표율 포함
- [ ] 투표 버튼과 결과 화면
- [ ] 투표와 집계 테스트 작성

**완료 기준**
- 같은 사용자가 같은 질문에 두 번 투표할 수 없다.
- 존재하지 않는 선택지를 보내면 저장되지 않는다.
- 투표 전에는 API 응답에 득표수와 득표율이 포함되지 않는다.
- 투표가 0개여도 오류가 나지 않는다.
- 득표율 합이 100%로 표시된다.

## 작업 규칙
- 모델은 코드를 쓰기 전에 필드와 관계부터 정리한다.
- 권한과 공개 범위는 화면이 아니라 API에서 보장한다.
- API 주소는 끝 슬래시 없이 `/api/questions/1` 형태로 통일한다.
- 코드는 직접 작성하고, 막히면 공식 문서를 먼저 찾아본 뒤 질문한다.
- 기능을 추가할 때 테스트도 함께 작성한다.
- 04 챕터 이후에는 기능을 끝낼 때마다 배포한다.
- 막혔던 내용은 `notes/`에 정리한다.
- 챕터마다 GitHub 이슈를 만들고, `main`에서 작업 단위 브랜치를 나눠 PR로 머지한다.
- PR은 Merge commit으로 머지하고, 챕터의 마지막 PR에 `Closes #이슈번호`를 쓴다.
